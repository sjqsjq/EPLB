### 1c. GPU 侧执行时间：任何工件中均无直接测量
perf_counter 只包 CPU 派发（scatter_add_ 核异步执行）；源码注释明言门/记录

### 1d. 更正后的两层表述
- CPU 账本层（实测）：record/scatter ≈ 3.6–4.1% wall/rank（稠密臂）、
  0.97–1.04%（稀疏臂）、3.7%（A 臂）；另 allreduce 0.7–3.7s、控制面 ≤0.44s。
- 服务时间可见层（经验上界）：F_sparse 相对 F_dense 每 rank 省 record CPU
  ~10.9s（W1）/~21.2s（W2），对应服务时间差 W1: +0.85/+3.87s（更慢）、
  W2: −3.62/+0.84s（b1 更快/b2 更慢）——符号不一致、幅度 ≤ 所省 CPU 的 ~17%
  → record CPU 大部分与 GPU 执行重叠被隐藏；服务时间可见份额 ≲0.5% wall。
- 原 "<0.1%" 撤回；正确说法："门+控制面 ≤0.06%（实测）；record CPU ~4%（实测，
  稠密）；其服务时间可见份额 ≲0.5%（臂间经验上界）"。Q5"机会不足"结论不变，
  但论据由"成本本身极小"更正为"4× 削减 CPU 账本 ~3% wall 却不能兑换成
  符号一致的服务时间收益"。

## ③ "首规划@64、首 swap@32" —— 定义、计数原点、顺序解释（含更正）

- 计数原点：bench 第一个 forward。cum_steps=Σ steps_actual（已提交 H 边界的
  真实步，空闲 forward 推进 sp_fwd 但不推进步计数）；cum_opps 同理按行累加。
- **first_swap@32 的定义**：首个 sp_swaps_started>0 的已提交 H 边界行 =
  sp_h_id 2（cum_steps=32）。S1 臂（A/F_dense）均为 h2@32 步；
  F_sparse 为 h2@128 步（H64 周期，≈45s）——首 swap 步数位置 4× 更晚。
- **"首规划@64" 是 P2 报告的标注错误**：该数字取自首个 event∉{hold,init} 行
  （confirmed_grow@h4, cum_steps=64）。但 event 字段是 v21 **窗口大小控制**
  协议事件（init/hold/confirmed_grow/confirmed_shrink/midband_hold…），
  在 SP 模式下其 W_after 永不应用（PD-8），confirmed_grow 不是布置方案；
  且 W 控制需 window-shift-confirm=2 连续确认（启动参数
  --pb-oeplb-window-shift-confirm 2），最早只能在第 3–4 边界出现。
- **真正的"首个有效规划"** = p2l_version（propose-to-load 布置方案版本）
  首次 >0：sp_h_id 2、cum_steps=32，且与首 swap **同一边界行**
  （该行 p2l=1, det_map=1, swaps_row=1）。时序：h1=init（检测 seeding，
  p2l=0）→ h2 首次检测聚合提交 p2l v1 → swap 立即开始 → h4 W 控制首个
  confirmed_grow（SP 下惰性）。
- **swap 从未先于规划**：所谓"先 swap 后规划"是把 W 控制事件误当规划事件
  的标注产物。三臂（A/F_dense/F_sparse）首规划与首 swap 都在 h2 同边界，
  完全一致。

## ④ TRACK/QUIET/RECOVER 占比 —— 真实 forward 驻留（替代窗口/周期数）

方法：按行 sp_state_before 分组（该周期实际运行态）。S1 态 forward 数 =
Σ sp_sample_opportunities **精确**（S1 门=每 forward 一次机会）；QUIET(S4)
forward ∈ [4Σopps−3/周期, 4Σopps+3/周期]（PD-9 块相位界）。
