## 第一部分：四点修正（原表述 → 修正后）

### 修正 1：窗口噪声解释尚未因果隔离
原表述（v1 §一.4）把 A10 在 prover 段的 cos 跌落（0.58–0.88，对照 A00 ≥0.958）归因为
"窗口收缩自致的采样噪声放大（自致振荡）"。
**修正**：这是一个与观察一致的假设，但未被因果隔离。A10 与 A00 的对比存在混杂：
(a) 两臂 swap 历史不同 → 布局分化 → 调度时序分化 → 每窗口打包的请求组合不同；
(b) 窗口边界位置不同；(c) cos 每 4 窗口采样点位置不同。且定量核算不支持"纯窗口减半"解释：
prover 段每窗口（W=16）约 256 条请求，若请求间路由方差主导，窗口减半使直方图样本方差×2，
由 A00 的 1−cos≈0.035 仅预测 A10 cos≈0.93，而实测均值 0.81 → 必有窗口大小之外的因素参与
（可能包括 cos 触发的 window_shift 反馈、布局/调度分化，均无法从日志分离）。
**可保留的事实性结论**：A10 的 ratio jump/shrink 事件在 prover 短提示段内密集出现
（13/31 个有值 jump 在段内、最大 0.493 在段内而非边界），且伴随该段 cos 显著低于同 α 固定窗臂。
归因（外生变化 vs 内生反馈 vs 调度分化）未定；因果隔离需要受控重放干预，本阶段不做、不提案。

### 修正 2：batch 组成未记录，不能断言 GPU batch 单域
原表述（v1 §一.2）称"段内 chunked prefill 打包的是同域请求"。
**修正**：per-batch/per-forward 域组成从未被记录，该句降级为**未验证假设**。
"边界过渡带 ~256 条请求（~10–12 s）"是模型化近似，依赖按序准入 + 完成序仅轻度重排的假设；
若调度器实质乱序准入，或长请求（code 平均 2048 tok）滞留造成跨边界拖尾，混合带可能更宽，
其方向与幅度无法由现有日志约束。结论表述统一改为："batch 级域组成不可判定；
客户端 3 次切域是事实，GPU 工作流过渡形态是推断（假设已注明）"。

### 修正 3：+10.4 s 是策略净差，不是纯控制成本
原表述在成本侧把 A11−A00=+10.40 s CI[+5.00,+15.80] 写作"adaptive 净服务成本 / adaptivity net cost"。
**修正**：该值是**两个完整策略的服务时间净差**（A11: W16, α=0.5, ADW on, D on vs A00: W16, α=0.0, off, off），
同时捆绑了 α 基线变化 + ADW + D 三个因素；战役中没有 (16, α=0.5, off, off) 臂，α 效应在任何对比中都未隔离。
最接近单模块的干净数字是 A10−A00=+4.79 s（α=0 下的 ADW 效应，CI 跨零）；D 无隔离对比。
论文与后续引用一律写作"策略净差（多因素）"，不得写作"控制器纯开销"。
break-even 讨论中 +10.4 s 只以"完整 adaptive 策略相对校准选定固定策略的实测净差（部署相关量）"身份出现。

### 修正 4：39% × 局部 replay gap 的乘法口径不一致
原表述（v1 §二 break-even）用 0.39（= 94×~1450 µs replay 口径层时间 ÷ ~350 ms/forward 服务墙钟）
乘以 replay 口径的 gap g 再乘 370 s。
**修正**：分子来自单层重放（捕获 batch ~4056 行、completion-fenced、无 attention/调度开销），
分母来自全服务墙钟/forward（batch ≤8192 tok、含 attention/采样/调度）——两者口径不同，
乘积无干净解释。修正后的纪律：
(a) gap g 只在 replay 口径内报告（µs/层·forward 及 %）；
(b) "专家执行占服务时间份额"仅作数量级旁注，显式给出区间（30–55%，取决于 batch 形状迁移假设）
并标注为假设栈而非测量；
(c) 任何"潜在服务级收益秒数"的换算都标注双重假设（份额 × 捕获率），仅作情景说明，
**pilot 判定绝不使用服务口径换算**（pilot 结论只陈述所选层与候选上是否存在跨域交叉优势）。

## 第三部分：缩小版跨域 replay pilot（CD-X0）—— 精确预算与分析口径（PROPOSED，未运行，待批准）

完整冻结文本见 `configs/followup_v1/cdx0_pilot_protocol.json`。要点：

- **问题（限定范围）**：在 2 个预选层上，4 个按域校准 greedy 布局在 4 个按域 evaluation 捕获行上
  是否表现出**明显的跨域交叉优势**（行追踪自身 base）。**不**据此宣布全服务有/无收益（两方向都不）。
- **层选择（预注册规则，仅用既有单域 crosstab 结果，未接触任何跨域数据）**：
  layer-024（同域 oracle gap 最小 0.00%）与 layer-071（最大 0.50%）→  bracket 两端。
- **矩阵**：每层 4 行（域 evaluation 捕获）× 5 列（identity + 4 个按域校准布局）= 20 计时单元；
  两层共 **40 个计时单元格**。每个 capture 在**同一进程**内重测全部 5 列（crosstab_v1 语义）。
- **独立启动与块内重复（明确）**：每 capture **4 个独立 start**（每 start 独立 torchrun 进程组、
  重载权重）；每 start 内 **5 个 block**；每 block 内 5 列按 (start,block) 轮转序全测
  （列内 10 initial + 10 activation warmup + 50 timed forwards，completion-fenced）。
  单元格估计 = 4 start 均值 ×（5 block 均值）；对比在 block 内配对、start 间配对，t-CI df=3。
- **捕获（16 单元，真实服务、真实请求）**：4 域 × 2 层 × {calibration 段捕获（**仅**用于建布局）、
  evaluation 段捕获（**仅**作为计时行)}。触发 = 既有 snapshot_split 机制，
  按客户端请求索引在各域**中点**触发（evaluation ~962/2936/4940/6947；calibration ~1037/3063/5060/7052），
  距任何边界 ≥700 条 ≫ 并发 256 → 域污染风险受限；但 batch 域纯度**不可直接验证**（修正 2 口径），预注册注明。
- **候选生成纪律**：布局仅由 calibration 捕获的路由计数经冻结 greedy builder（与 crosstab_v1 base 同代码同参数）构建；
  evaluation 捕获绝不进入布局构建、不用于挑选 capture、不用于挑选列；无 best-start/best-block；
  失败 start 退役不重试；有效 start <3 的行 = indeterminate（每层 ≥2 行 indeterminate → 该层 indeterminate）。
- **判定（预注册，replay 口径）**：每行 3 个配对对比 T(x_d,L_d')−T(x_d,L_d)，t975(df=3)=3.182，
  实用等价 margin ε=22.948 µs（沿用 crosstab_v1 口径）；row_tracks_own_base = 3 个 CI 全部正向排除零；
  clear_crossover(layer) = ≥2/4 行追踪；verdict：≥1 层 clear → "所选层与候选上检测到跨域交叉优势"；
  0 层 → "未检测到"；其余 → "不确定"。**verdict 措辞不含任何全服务收益断言。**
- **次要描述量（不进判定）**：oracle gap（T_static,cand vs T_switch,cand），行等权与 K̃ 加权各报一份；
  K̃_d=evaluation token 份额 (0.157/0.120/0.237/0.486)，**注明假设**：token 份额近似域对服务负载的贡献，
  而 replay 行按设计近似等行数，故 K̃ 加权是外生的服务相关性近似权重，非 replay 测量量；不做任何 ×39% 类换算。
- **精确预算**：重放 = 8 个 capture-campaign × 4 starts = **32 个独立 start**（非 160）；
  按 crosstab_v1 实测 ~12 min/start ≈ **6.4 GPU-h**；捕获 = 2 个真实服务运行（calibration 段 + evaluation 段，
  各含 boot ~20 min + 至最后触发点 ~5 min）≈ **1 GPU-h**；布局构建/分析 CPU 级 <1 h。
  **合计 ≈ 7.5–8 GPU-h（一个运行日内）**。任何超过 40 单元格的扩展需另行预注册，不自动升级。
- **机会 vs 可利用性分离**：重放 harness 不含控制器 → pilot 只回答"机会是否存在（所选层、所选候选）"。
  "旧控制器能否利用机会"由第二部分日志核查（检测锁定率、阈值级再触发率、W 偏离、累计成本）单独回答；
  若未来修改控制器，只在 calibration 上开发验证，五臂旧结果原样保留，不改写、不重跑。
