# Sync Window × Input/Output Length 实验日志 (2026-07-25~26)

## 实验环境
- **硬件**: 8× NVIDIA H20 (96GB/卡, NVLink NV18 全互连, 无IB/RDMA)
- **模型**: Qwen3-235B-A22B-FP8, EP=8, DP=8
- **deepep-mode**: auto（所有配置统一）
- **OEPLB参数**: threshold=1.02, min_prefill_tokens=256, cooldown=5, max_total_swap_layers=94, max_swaps_per_layer=64
- **数据集来源**: DeepSeek-Prover-V1 (Lean4定理证明)

## 数据集构造说明（重要！）

当前所有实验使用的数据集由 `build_length_grid.py` 生成，构造方法如下：

| 长度档 | 构造方法 | 内容特征 |
|--------|---------|---------|
| tok256 (220-290 tok) | 从Prover-V1源按token范围筛选**自然prompt** | 每条是完整的单个Lean4定理+goal |

### 方法

## 实验五：方法论修复 + 真实DeepSeek-Prover-V1数据集验证 (2026-07-27)

### 发现并修复的三个测试方法论Bug

**Bug 1: 压测warmup连接池预热不充分**
- 问题：原始脚本只用5条串行请求做warmup，不足以预建立全部并发TCP连接。高并发(conc=256/1024)时，正式计时开始后aiohttp需要现场建立大量连接，建连耗时（OS调度依赖，run-to-run不确定）被计入计时窗口
- 影响：L=256/O=1短benchmark里导致高达±25%的run-to-run方差，完全掩盖了真实信号
- 修复：warmup改为用`/health`端点发`conc`个并发GET请求（不经过模型forward pass），预热连接池但不污染OEPLB状态

**Bug 2: warmup发真实模型请求污染OEPLB计数器**
- 问题：第一版修复用`conc`个假prompt做warmup，虽然不再因数据集大小而变化，但这些请求仍然走模型forward pass，会被OEPLB的`record_next_layer()`记录+推进`sync_window`计数器
- 影响：当conc=1024=数据集大小N时，warmup阶段的1024个假请求+正式阶段的1024个真请求=服务器实际处理2048个请求（比预期翻倍），且OEPLB的swap决策可能基于假数据的路由分布做出
- 修复：warmup改用`/health`端点（完全不触发模型推理），确认POST计数精确等于数据集大小

**Bug 3: 编排脚本关服务器后固定sleep不检查GPU显存清零**
- 问题：服务器SIGTERM后固定sleep 8秒就启动下一个，但实际GPU显存释放时间不确定（残留进程/driver cleanup），下一个服务器可能启动时显存还没完全回收
- 修复：shutdown后用nvidia-smi轮询等待显存降到<500MiB再继续

## 代码优化：min_swap_ops 过滤机制 (2026-07-27)

### 动机

从L=256/sw=8日志观察到：冷启动后ratio迅速稳定在~1.207，后续每个window只算出1-6个需要swap的ops，但每次仍然要付`batch_isend_irecv`的跨rank同步开销（~330-350ms/次）——全程64个window里58个都是这种"高成本低收益"的操作。

### 实现

在`controller.py`的`_decide_and_begin_swap()`中，`try_build_swap_plan()`返回plan后、`async_executor.begin(plan)`之前，检查`len(plan) < cfg.min_swap_ops`——如果是，跳过P2P传输，只记录skip日志。

```python
if len(plan) < self.cfg.min_swap_ops:
    logger.info(f"[PB-OEPLB] window#{self.window_count}: skipped "
               f"{len(plan)} swap(s) (< min_swap_ops={self.cfg.min_swap_ops})")
    return
```

### 效果

L=512场景下（sw=8, min_swap_ops=8, 8192条请求）：
- 总共64个window，只有3个真正执行了swap（234+52+8=294次），61个被skip
- 每个被skip的window省掉~330ms的P2P开销，总共省了~20秒
- 不影响冷启动纠偏效果（前2个window的重纠偏完全保留）

### CLI参数

`--pb-oeplb-min-swap-ops N`（默认1，即不过滤。推荐设为8）
